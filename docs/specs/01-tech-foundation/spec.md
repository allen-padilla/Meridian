# 01 — Tech Foundation

## Stack

| Layer | Choice |
|---|---|
| Backend framework | Laravel 13, PHP 8.4 |
| Frontend/SPA bridge | Inertia.js v3 |
| UI framework | React 19 |
| Styling | Tailwind CSS v4 |
| Component library | shadcn/ui |
| Typed route generation | Laravel Wayfinder |
| OAuth2 / API auth | Laravel Passport v13 (client-credentials grant for the player portal API) |
| Social/SSO login | Laravel Socialite v5 |
| Testing | Pest v4 (PHPUnit 12 underneath) |
| Formatting (PHP) | Laravel Pint |
| Formatting/linting (JS/TS) | Prettier + ESLint v9 |
| Local dev database | SQLite |
| Production database target | PostgreSQL |
| Local dev process runner | `laravel/pail` for logs, `concurrently` for multi-process `dev` |

This is a deliberately boring, conventional Laravel + Inertia stack. The
interesting decisions in this system are in the data model and business
rules (see the later specs), not in tooling choices.

## Repository structure

Standard Laravel layout. Notable non-default choices to preserve:

- `app/Http/Controllers/Api/` — controllers for the player portal API,
  kept separate from the guildkeeper-facing web controllers in
  `app/Http/Controllers/` even where they manage the same resource (e.g.
  `Api\HeroController` vs `HeroController`). The two have different
  authorization models and almost no shared logic beyond the Eloquent
  models, so merging them would mean branching on request source inside
  a single controller — worse than two small, single-purpose ones.
- `app/Support/` — small framework-agnostic helper classes used by more
  than one controller (e.g. a shared data-cleaning routine used by both a
  CSV importer and a manual-entry form), kept out of the model layer so
  models stay focused on persistence and relationships.
- `resources/js/pages/` — one file per Inertia page, organized into
  subfolders that mirror the URL structure (`heroes/`, `quests/`,
  `settings/`).
- `resources/js/actions/` and `resources/js/routes/` — generated by
  Wayfinder; never hand-edited. Regenerate with
  `php artisan wayfinder:generate` after any route change.

## Commands

```bash
composer run dev          # start all processes: PHP server, queue, pail logs, Vite
composer run setup        # fresh install: composer + npm install, key:generate, migrate, npm build
composer run lint         # run Pint formatter
composer run lint:check   # check formatting without fixing
composer run ci:check     # full CI check: lint, format, types, tests
php artisan test --compact                          # run all tests
php artisan test --compact --filter=TestName        # run a single test
vendor/bin/pint --dirty --format agent              # format only changed PHP files (run after edits)
npm run build             # compile frontend assets
npm run dev               # Vite dev server only
npm run types:check       # TypeScript type check
npm run lint:check        # ESLint check
npm run format:check      # Prettier check
```

## Build order

This guide is written so each numbered folder can be implemented roughly in
order, with later specs depending on entities the earlier ones introduce:

1. **Auth & roles** first — every other feature is gated behind guildkeepers login.
2. **Heroes** next — quests reference heroes, not the other way around.
3. **Quests** (enlistments, wanderers, muster) — depends on Heroes
   existing.
4. **External sync API** — depends on both Heroes and Quests existing,
   since it writes to both.
5. **Dashboard** and **data import/export** — read/aggregate over the
   above; build last so there's real data to build against.
6. **Frontend/UX conventions** apply throughout, but are written up last
   since they're easiest to describe once concrete pages exist to point to.

## Non-goals for this foundation

- No multi-tenancy. One Guild, one deployment.
- No queue-backed background processing beyond what Laravel's default
  queue worker handles for framework needs (e.g. Passport's cleanup
  commands) — imports and syncs in this system are small enough (hundreds,
  not millions, of rows) to run synchronously within a request.
- No API versioning scheme for the player portal API — it has exactly one
  consumer (the Guild's own player portal), deployed in lockstep
  with this system, so versioning would be speculative complexity.
